# منظومة مبيعات المراسل للمقاهي

نظام نقاط بيع لمقهى واحد.

## التقنية

- الباكند: FastAPI + Python
- قاعدة البيانات: SQLite
- الواجهة: React + Vite + TypeScript + Tailwind في `frontend/`
- الباكند في حزمة `app/`

## هيكل المجلدات

ثلاث طبقات فقط: المسار، الخدمة، والنموذج. لا طبقة `repositories` ولا حاوية حقن اعتماديات.

```text
app/
  main.py
  core/          config.py  security.py  deps.py
  db/            base.py  session.py
  models/        user  category  product  shift  sale  audit_log
  schemas/       نفس التقسيم
  routers/       auth  categories  products  shifts  sales  reports  audit
  services/      نفس التقسيم
  utils/         money.py  time.py
alembic/
tests/
frontend/
  src/
    app/           App.tsx  routes.tsx
    api/           axios + مسارات الباكند
    types/         common  entities  requests
    shared/        ui  layout  auth
    pages/         login + admin/* + cashier/*  (page.tsx + components/)
    context/       AuthContext
    utils/         money  storage
```

- `routers`: يستقبل الطلب، يتحقق من الصلاحية، يستدعي الخدمة، ويرجع المخطط. لا قواعد عمل هنا.
- `services`: قواعد العمل (وردية واحدة مفتوحة للكاشير، لا بيع بدون وردية، الإلغاء، التقارير على `completed` فقط، وكتابة `audit_logs`).
- `models` و `schemas`: الجداول وعقود الطلب والاستجابة. `sale.py` يجمع `Sale` و `SaleItem` لأنهما يُقرآن ويُكتبان معًا.
- `utils`: دوال صافية فقط، مثل تحويل المبلغ ونطاقات اليوم والأسبوع والشهر.
- `core`: الإعدادات، وتجزئة كلمة المرور، ورمز JWT، والاعتماديات المشتركة.
- `db`: محرك SQLAlchemy وجلسة قاعدة البيانات.

لا مجلد لكل ميزة (`features/sales/...`). إذا كبر ملف خدمة لاحقًا يُقسَّم داخل `services/` دون إضافة طبقة جديدة.

## المكتبات

- `fastapi` و `uvicorn`: التطبيق والخادم.
- `sqlalchemy` و `alembic`: الجداول والهجرات على SQLite، حتى يبقى الانتقال لاحقًا ممكنًا دون إعادة كتابة الخدمات.
- `pydantic-settings`: قراءة الإعدادات من البيئة.
- `pwdlib` مع `bcrypt`: تجزئة كلمات المرور.
- `PyJWT`: رمز دخول للمدير والكاشير، مناسب لواجهة React لاحقًا.
- `pytest` و `httpx`: اختبارات المسارات.
- `tzdata`: بيانات المناطق الزمنية على ويندوز، حتى تُحسب التقارير بتوقيت طرابلس.

واجهة React:

- `react-router-dom`: المسارات حسب الدور.
- `axios`: استدعاء `/api` مع JWT.
- `tailwindcss`: تنسيق شاشة لمس.

لا Redis ولا Celery ولا Docker ولا PostgreSQL في هذه النسخة.

- العملة: **دينار ليبي (د.ل)**. المستخدم يدخل الدينار (مثل `1` أو `1.5`). الـ API يعيد `price_lyd` و`total_lyd` وما شابه. التخزين داخلياً بالأدرهم (ألف جزء من الدينار).
- المصادقة برمز JWT يحمل الدور: `admin` أو `cashier`.

## داخل النسخة الأولى

- مستخدمون: مدير (`admin`) وكاشير (`cashier`)
- تصنيفات ومنتجات: تعطيل/تفعيل، وحذف فقط إن لم يظهر المنتج في أي فاتورة. حذف تصنيف يُرفض إن بُيع أحد منتجاته، ويُسمح إن لم يُبع أي منها (وتُحذف منتجاته غير المباعة معه)
- وردية صندوق: فتح ثم بيع ثم إقفال
- فاتورة بطريقة دفع واحدة: نقدي (`cash`) أو بطاقة (`card`)
- إلغاء فاتورة بدون تعديل. من يريد التصحيح يلغي الفاتورة وينشئ فاتورة جديدة
- سجل نشاط (`audit`) للمدير: إنشاء وإلغاء
- تقارير: اليوم، الأسبوع، الشهر، وحسب الوردية

## خارج النسخة الأولى

- تعديل فاتورة
- خلط نقدي وبطاقة في نفس الفاتورة
- طاولات، ويتر، مطبخ، توصيل
- مرتجعات جزئية، خصومات متقدمة، فروع، موردون، مخزون معقّد

## الجداول (المرحلة الأولى)

```text
users
categories
products
shifts
sales          payment_method + status + shift_id
sale_items
audit_logs
```

قواعد مختصرة:

- كاشير واحد = وردية واحدة مفتوحة
- لا بيع بدون وردية مفتوحة
- الفاتورة إما `completed` أو `cancelled`، ولا تُحذف
- التقارير تحسب الفواتير المكتملة فقط
- الكاشير يلغي فاتورة ورديته وهي مفتوحة. المدير يلغي في أي وقت
- كل إنشاء وإلغاء يُسجَّل في `audit_logs` ويظهر للمدير فقط
- لا حذف فعلي للفاتورة. المنتج أو التصنيف الذي ظهر في فاتورة لا يُحذف؛ يُعطَّل بدل ذلك. محاولة الحذف تُرجع 409 وتظهر رسالة في الواجهة

## شاشات الواجهة

- تسجيل الدخول
- مدير: مستخدمون، تصنيفات، منتجات، تقارير، سجل نشاط، إلغاء فاتورة برقمها
- كاشير: وردية (فتح/إقفال)، نقطة بيع (منتجات + سلة + نقدي/بطاقة + إلغاء آخر فاتورة)

كل صفحة في `frontend/src/pages/.../page.tsx` مع مكوّناتها في `components/`. العناصر المشتركة في `shared/`.

## ترتيب بناء الباكند

1. المستخدمون وتسجيل الدخول
2. التصنيفات والمنتجات
3. الورديات (فتح / الحالية / إقفال)
4. المبيعات والإلغاء
5. التقارير وسجل النشاط

## التشغيل

المجلد الجذر للمشروع: `almurasel pos_system`. التطبيق في `app.main` وليس `main` في الجذر.

### أول مرة (إعداد)

من PowerShell في جذر المشروع:

```powershell
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m alembic upgrade head
cd frontend
npm install
cd ..
```

### الباكند (نافذة طرفية)

```powershell
cd "C:\Users\asus\Desktop\almurasel pos_system"
.\.venv\Scripts\Activate.ps1
python -m uvicorn app.main:app --reload --port 8000
```

- API: `http://127.0.0.1:8000/api`
- توثيق Swagger: `http://127.0.0.1:8000/docs`

### الواجهة (نافذة طرفية ثانية)

```powershell
cd "C:\Users\asus\Desktop\almurasel pos_system\frontend"
npm run dev
```

- الواجهة: `http://localhost:5173`
- طلبات `/api` تُوجَّه إلى الباكند عبر بروكسي Vite (يحتاج الباكند شغّال على المنفذ 8000).

### فحص الباكند

```powershell
.\.venv\Scripts\Activate.ps1
python -m pytest
```

### بيانات الدخول الافتراضية

عند أول تشغيل، إذا كان جدول المستخدمين فارغًا، يُنشأ مدير:

- المستخدم: `admin`
- كلمة المرور: `admin123`

غيّر `JWT_SECRET` في `.env` قبل أي استخدام خارج الجهاز. المبالغ بالدينار الليبي في الواجهة والـ API، وأسبوع التقارير يبدأ السبت بتوقيت طرابلس.

### إعادة قاعدة البيانات من الصفر

أوقف الباكند أولاً، ثم من جذر المشروع:

```powershell
.\.venv\Scripts\Activate.ps1
python scripts\reset_database.py
```

يُحذف ملف `pos.db`، تُنشأ الجداول من جديد، ثم تُضاف تلقائياً:

- مدير افتراضي (`admin` / `admin123`)
- تصنيفات: مشروبات، عصائر طبيعية، قهوة، سندوتشات، حلويات
- منتجات تجريبية: قهوة عادية (3 د.ل)، قهوة دبل (5 د.ل)، ماء (1 د.ل)

عند أول تشغيل للباكند على قاعدة فارغة يُنفَّذ نفس البذور تلقائياً (`seed_on_startup`).
