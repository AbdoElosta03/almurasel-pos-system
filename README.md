# منظومة مبيعات المراسل للمقاهي

نظام نقاط بيع لمقهى واحد.

## التقنية

- الباكند: FastAPI + Python
- قاعدة البيانات: SQLite
- الواجهة: React + Vite + TypeScript + Tailwind في `frontend/`
- الباكند في حزمة `app/`

## هيكل المجلدات

ثلاث طبقات فقط: المسار، الخدمة، والنموذج. لا طبقة `repositories` ولا حاوية حقن اعتماديات.

```text
app/
  main.py
  core/          config.py  security.py  deps.py
  db/            base.py  session.py
  models/        user  category  product  shift  sale  audit_log
  schemas/       نفس التقسيم
  routers/       auth  categories  products  shifts  sales  reports  audit
  services/      نفس التقسيم
  utils/         money.py  time.py
alembic/
tests/
frontend/
  src/
    app/           App.tsx  routes.tsx
    api/           axios + مسارات الباكند
    types/         common  entities  requests
    shared/        ui  layout  auth
    pages/         login + admin/* + cashier/*  (page.tsx + components/)
    context/       AuthContext
    utils/         money  storage
```

- `routers`: يستقبل الطلب، يتحقق من الصلاحية، يستدعي الخدمة، ويرجع المخطط. لا قواعد عمل هنا.
- `services`: قواعد العمل (وردية واحدة مفتوحة للكاشير، لا بيع بدون وردية، الإلغاء، التقارير على `completed` فقط، وكتابة `audit_logs`).
- `models` و `schemas`: الجداول وعقود الطلب والاستجابة. `sale.py` يجمع `Sale` و `SaleItem` لأنهما يُقرآن ويُكتبان معًا.
- `utils`: دوال صافية فقط، مثل تحويل المبلغ ونطاقات اليوم والأسبوع والشهر.
- `core`: الإعدادات، وتجزئة كلمة المرور، ورمز JWT، والاعتماديات المشتركة.
- `db`: محرك SQLAlchemy وجلسة قاعدة البيانات.

لا مجلد لكل ميزة (`features/sales/...`). إذا كبر ملف خدمة لاحقًا يُقسَّم داخل `services/` دون إضافة طبقة جديدة.

## المكتبات

- `fastapi` و `uvicorn`: التطبيق والخادم.
- `sqlalchemy` و `alembic`: الجداول والهجرات على SQLite، حتى يبقى الانتقال لاحقًا ممكنًا دون إعادة كتابة الخدمات.
- `pydantic-settings`: قراءة الإعدادات من البيئة.
- `pwdlib` مع `bcrypt`: تجزئة كلمات المرور.
- `PyJWT`: رمز دخول للمدير والكاشير، مناسب لواجهة React لاحقًا.
- `pytest` و `httpx`: اختبارات المسارات.
- `tzdata`: بيانات المناطق الزمنية على ويندوز، حتى تُحسب التقارير بتوقيت طرابلس.

واجهة React:

- `react-router-dom`: المسارات حسب الدور.
- `axios`: استدعاء `/api` مع JWT.
- `tailwindcss`: تنسيق شاشة لمس.

لا Redis ولا Celery ولا Docker ولا PostgreSQL في هذه النسخة.

- العملة: **دينار ليبي (د.ل)**. المستخدم يدخل الدينار (مثل `1` أو `1.5`). الـ API يعيد `price_lyd` و`total_lyd` وما شابه. التخزين داخلياً بالأدرهم (ألف جزء من الدينار).
- المصادقة برمز JWT يحمل الدور: `admin` أو `cashier`.

## داخل النسخة الأولى

- مستخدمون: مدير (`admin`) وكاشير (`cashier`)
- تصنيفات ومنتجات: تعطيل/تفعيل، وحذف فقط إن لم يظهر المنتج في أي فاتورة. حذف تصنيف يُرفض إن بُيع أحد منتجاته، ويُسمح إن لم يُبع أي منها (وتُحذف منتجاته غير المباعة معه)
- وردية صندوق: فتح ثم بيع ثم إقفال
- فاتورة بطريقة دفع واحدة: نقدي (`cash`) أو بطاقة (`card`)
- إلغاء فاتورة بدون تعديل. من يريد التصحيح يلغي الفاتورة وينشئ فاتورة جديدة
- سجل نشاط (`audit`) للمدير: إنشاء وإلغاء
- فواتير مشتريات للمدير: تاريخ شراء، مورد اختياري، وعناصر باسم المادة والكمية وسعر إجمالي لكل بند؛ لا تتأثر بها أسعار البيع أو المخزون
- تقارير: اليوم، الأسبوع، الشهر، وحسب الوردية

## خارج النسخة الأولى

- تعديل فاتورة
- خلط نقدي وبطاقة في نفس الفاتورة
- طاولات، ويتر، مطبخ، توصيل
- مرتجعات جزئية، خصومات متقدمة، فروع، موردون، مخزون معقّد

## الجداول (المرحلة الأولى)

```text
users
categories
products
shifts
sales          payment_method + status + shift_id
sale_items
audit_logs
purchases
purchase_items
```

قواعد مختصرة:

- كاشير واحد = وردية واحدة مفتوحة
- لا بيع بدون وردية مفتوحة
- الفاتورة إما `completed` أو `cancelled`، ولا تُحذف
- التقارير تحسب الفواتير المكتملة فقط
- الكاشير يلغي فاتورة ورديته وهي مفتوحة. المدير يلغي في أي وقت
- كل إنشاء وإلغاء يُسجَّل في `audit_logs` ويظهر للمدير فقط
- فواتير المشتريات منفصلة عن فواتير البيع. إجمالي فاتورة الشراء هو مجموع أسعار البنود المدخلة، دون ضرب السعر في الكمية
- لا حذف فعلي لفواتير البيع. يمكن للمدير حذف فاتورة مشتريات وبنودها بعد تأكيد؛ يُسجّل الحذف في سجل النشاط. المنتج أو التصنيف الذي ظهر في فاتورة بيع لا يُحذف؛ يُعطَّل بدل ذلك. محاولة الحذف تُرجع 409 وتظهر رسالة في الواجهة

## شاشات الواجهة

- تسجيل الدخول
- مدير: مستخدمون، تصنيفات، منتجات، تقارير، سجل نشاط، إلغاء فاتورة برقمها
- كاشير: وردية (فتح/إقفال)، نقطة بيع (منتجات + سلة + نقدي/بطاقة + إلغاء آخر فاتورة)

كل صفحة في `frontend/src/pages/.../page.tsx` مع مكوّناتها في `components/`. العناصر المشتركة في `shared/`.

## التشغيل

### طباعة USB المباشرة على ويندوز

- تُرسل الفاتورة من الخادم إلى طابعة `xprinter` باستخدام ESC/POS بصورة تدعم العربية، بدل نافذة طباعة المتصفح.
- ثبّت متطلبات `requirements.txt` على كمبيوتر المحل وأعد تشغيل الخادم. يجب أن تكون الطابعة مثبتة على **نفس كمبيوتر الخادم**، وأن يملك حساب تشغيل الخادم صلاحية استخدامها.
- الاسم الافتراضي `xprinter` (دون حساسية لحالة الأحرف). يمكن تغييره في `.env` باستخدام `RECEIPT_PRINTER_NAME=xprinter`، والمهلة الافتراضية `RECEIPT_PRINT_TIMEOUT_SECONDS=10`.
- من إعدادات الكاشير اضغط «فحص الطابعة»، ثم جرّب بيعًا واحدًا مع الورق، وبعدها جرّب مع نفاد الورق. هذه التجربة تطبع فاتورة فعلية.
- إذا أبلغ ويندوز عن عطل أو وجود مهمة معلقة فلن تُضاف فاتورة جديدة. المهمة الجديدة التي تفشل أو تبقى أكثر من المهلة يُطلب إلغاؤها **وحدها**؛ لا تُحذف مهام أخرى ولا توجد إعادة إرسال تلقائية. تبقى المبيعات محفوظة.
- توقف واجهة الكاشير الطباعة تلقائيًا بعد أي فشل حتى يعيد المستخدم تفعيلها من الإعدادات بعد معالجة السبب.
- إغلاق نافذة المتصفح أو فقدان الرد لا يعيد طباعة نفس الفاتورة: محاولة الإرسال تُسجل في سجل النشاط. التشغيل مدعوم بخادم واحد (`--workers 1`) فقط.
- **مهم:** بعض تعريفات USB لا تبلغ عن نفاد الورق، وقد تُخرج المهمة من طابور ويندوز بمجرد نقلها إلى ذاكرة الطابعة. انتهاء المهمة ليس إثباتًا لخروج الورق، ولا يمكن إلغاء بيانات أصبحت داخل ذاكرة الجهاز بهذه الطريقة. لا ضمان لمنع التراكم على هذا التعريف قبل اختباره فعليًا.
- قبل الانتقال من الطريقة القديمة، أوقف الطباعة وألغِ المهام القديمة من طابور ويندوز يدويًا. البرنامج لا يمسح الطابور القديم تلقائيًا ولا يرجع لطباعة المتصفح عند الفشل.

المجلد الجذر للمشروع: `almurasel pos_system`. التطبيق في `app.main` وليس `main` في الجذر.

### بيانات الدخول الافتراضية

### استعادة كلمة مرور المدير

هذه الميزة غير مفعّلة افتراضياً ما لم يُضبط `ADMIN_RECOVERY_KEY` في `.env` بطول 8 أحرف على الأقل. يُنصح بمفتاح عشوائي طويل؛ لإنشائه على جهاز الباك اند استخدم:

```powershell
.\.venv\Scripts\python.exe -c "import secrets; print(secrets.token_urlsafe(48))"
```

احفظ القيمة الناتجة في ملف `.env` في جذر المشروع: `ADMIN_RECOVERY_KEY=القيمة_العشوائية`، ثم أعد تشغيل الباك اند. إذا اخترت مفتاحاً قصيراً مثل `4433AABB` فهو أضعف ويمكن تخمينه أو تداوله بسهولة أكبر؛ لا تعرّض واجهة الاستعادة للإنترنت بمفتاح كهذا، وغيّره إلى مفتاح طويل قبل النشر. لا تضع المفتاح في كود الفرونت اند أو في git، واحفظه لدى مسؤول النظام فقط. نفّذ `python -m alembic upgrade head` قبل استخدام النسخة الجديدة.

في صفحة تسجيل الدخول، اضغط شعار المراسل ثلاث مرات متتالية لفتح نموذج الاستعادة. أدخل اسم المدير، مفتاح الاستعادة، وكلمة المرور الجديدة مرتين. يستدعي النموذج `POST /api/auth/recover-admin`؛ يمكن استخدامه دون تسجيل دخول، لكن يتطلب المفتاح. تُحد المحاولات الخاطئة بخمس خلال 15 دقيقة لكل عنوان IP (داخل عملية الباك اند)، وتبطل جلسات الحساب القديمة عند النجاح. إخفاء النموذج ليس حماية بحد ذاته؛ إذا أُطلع شخص آخر على المفتاح فغيّره في `.env` وأعد تشغيل الباك اند.

### النسخ الاحتياطي

من إعدادات المدير يمكن إنشاء نسخة يدوية وتنزيل أي نسخة محفوظة. ينشئ الخادم نسخة تلقائية عند بدء تشغيله إذا لم توجد نسخة تلقائية سابقة، ثم كل 20 يوماً من آخر نسخة تلقائية ناجحة؛ يتحقق من الموعد عند التشغيل ومرة كل ساعة ما دام الخادم يعمل. النسخ اليدوية لا تغير هذا الموعد. تُنشأ النسخة باستخدام SQLite online backup بعد التحقق من سلامتها.

تُخزّن الملفات افتراضياً في مجلد `backups/` بجذر المشروع (مستبعد من git)، ويمكن تغيير المكان بوضع `BACKUP_DIR=D:/POS/backups` في `.env`. يحتفظ النظام بآخر نسخة فقط (يدوية أو تلقائية أو نسخة أمان)، ويحذف النسخ الأقدم بعد نجاح إنشاء النسخة الجديدة؛ وتُحتسب فترة النسخ التلقائي من تاريخ آخر نسخة محفوظة. يُفضّل حفظ نسخة خارجية على قرص آخر لأن فقدان النسخة الوحيدة يعني فقدان وسيلة الاستعادة. يمكن تعطيل الجدولة بوضع `BACKUP_AUTO_ENABLED=false`. الملفات تحتوي جميع بيانات الحسابات، لذا لا تشاركها مع غير المخوّلين.

### الاستعادة

من صفحة قاعدة البيانات يمكن استعادة نسخة محفوظة أو رفع ملف SQLite `.db` (حتى 512 MB). **هذه عملية استبدال كامل وليست دمجاً**: تتحقق من سلامة الملف والعلاقات وإصدار المخطط ووجود مدير نشط، وتتطلب كلمة مرور المدير الحالية وتأكيداً كتابياً. ينشئ النظام نسخة أمان باسم `safety-...db` قبل الاستبدال، ويوقف طلبات API الأخرى أثناء الاستعادة، ثم يبطل رموز الدخول القديمة؛ سجّل الدخول ببيانات الحسابات الموجودة في النسخة المستعادة. إذا اختلف إصدار قاعدة البيانات القديمة عن الإصدار الحالي، ارفع إصدار النسخة القديمة بشكل منفصل أولاً قبل استعادتها. تأكد من وجود مساحة كافية للنسخة المرفوعة ونسخة الأمان. يفضّل تنفيذ الاستعادة عندما لا يعمل كاشير على النظام.

### حذف البيانات وبدء جديد

من صفحة قاعدة البيانات يمكن للمدير اختيار «حذف البيانات وتفعيل السيدر». يتطلب كلمة مرور المدير الحالية وكتابة «حذف البيانات» للتأكيد. تحفظ العملية نسخة أمان `safety-...db` أولاً، ثم في معاملة واحدة تحذف المبيعات والمشتريات والورديات وسجل النشاط والمنتجات والتصنيفات وجميع الحسابات الأخرى، وتُبقي **حساب المدير الذي طلب العملية وكلمة مروره الحالية**. بعدها يعيد السيدر التصنيفات والمنتجات الافتراضية فقط، دون إنشاء مدير بكلمة مرور افتراضية. تُبطل جلسات الدخول السابقة، ولا تُحذف ملفات النسخ الاحتياطية أو مخطط القاعدة. يُفضّل تنفيذها خارج ساعات عمل الكاشير.

### إعادة قاعدة البيانات من الصفر

أوقف الباكند أولاً، ثم من جذر المشروع:

```powershell
.\.venv\Scripts\Activate.ps1
python scripts\reset_database.py
```

يُحذف ملف `pos.db`، تُنشأ الجداول من جديد، ثم تُضاف تلقائياً:

- مدير افتراضي (`admin` / `1234`)
- تصنيفات: مشروبات، عصائر طبيعيه، قهوة، سندوتشات، حلويات
- 24 صنفاً افتراضياً مع صور SVG خفيفة (قهوة، حلويات، عصائر، مشروبات، وسندوتشات) حسب القائمة في `app/services/seed.py`؛ يبدأ السيدر بقهوة عادية (3 د.ل) وقهوة دبل (5 د.ل)، وسعر «مالفي عادي» وقنينة الماء دينار واحد لكل منهما.

عند أول تشغيل للباكند على قاعدة فارغة يُنفَّذ نفس البذور تلقائياً (`seed_on_startup`).

تحديث السيدر لا يغير المنتجات أو الأسعار في قاعدة موجودة. لتطبيق القائمة على قاعدة موجودة استخدم «حذف البيانات وتفعيل السيدر» من صفحة قاعدة البيانات **فقط إذا أردت حذف كل بيانات العمل**؛ سيُحفظ ملف أمان قبل الحذف. لا تُنفّذ العملية لمجرد تحديث أسعار المنتجات الحالية.
